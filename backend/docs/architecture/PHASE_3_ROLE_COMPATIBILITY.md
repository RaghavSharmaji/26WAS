# Phase 3 Legacy Role Compatibility Assessment

**Status:** Assessment only. No role values or user/membership records were changed. No migration was run.

## Storage and resolution model found in source

- `backend/model/User.js` accepts global `User.role` values `super_admin`, legacy `superadmin`, `admin`, and `staff`; the auth boundary returns canonical `super_admin` for either stored Super Admin identifier.
- `backend/model/CompanyMembership.js` stores membership roles `company_admin`, `warehouse_manager`, `inventory_manager`, `procurement_manager`, `warehouse_staff`, `staff`, and `auditor`.
- `backend/middleware/permissions.js` derives `legacy_admin` or `legacy_staff` when an authenticated user has no company membership but is using the old ownerId boundary. These are permission-context aliases, not stored role values.
- Super Admin provisioning and platform guards historically use `superadmin`; the approved boundary adapter canonicalizes it to `super_admin`, with both identifiers retaining platform-only policy. The frontend still consumes the legacy identifier and must be coordinated after backend Milestone 2 verification.
- `backend/scripts/migrateCompanies.js` currently accepts the noncanonical membership roles as explicit mapping values. This is migration validation behavior only; it does not migrate roles in this assessment.
- `clearance` also stores historical labels such as `superadmin`, `admin`, and `staff`; authorization is based primarily on `User.role` and active membership, not that array.

## Safe compatibility rules

1. Never change `User.role` or `CompanyMembership.role` values as a side effect of login, startup, frontend company selection, or normal API requests.
2. Never derive Company Admin from global `admin` or `clearance` alone. Require an explicit, reviewed company membership.
3. Keep `legacy_admin`/`legacy_staff` in an ownerId-only context; they are not tenant roles. Future permission IDs must not be covered by a wildcard legacy grant.
4. Do not allow noncanonical `inventory_manager` or `procurement_manager` values to gain canonical privileges by fallback. Unsupported operations must fail closed until a separately approved mapping exists.
5. `staff` needs context-aware handling: a global user role and a membership role are different records and cannot share an unqualified alias.
6. Canonicalize `superadmin` to `super_admin` at one auth/authz boundary. Keep persisted values unchanged; both values must receive identical platform-only policy. New provisioning uses `super_admin` where supported.
7. Warehouse Managers and Staff may read company-wide catalog reference data within their active company for assigned-warehouse tasks. This does not grant catalog mutations. Warehouse inventory/stock remains assignment-scoped.
8. Map order handlers by behavior: `/create` creates; `PUT /:id/status` updates status but does not approve; `/submit` is currently read-only, broken, and ambiguous, so remains unmapped/fail-closed. Do not invent `order.submit` or approval behavior. Transfers and returns are deferred because no corresponding routes were found.
